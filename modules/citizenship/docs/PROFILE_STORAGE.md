# Personal profile storage

The Brain reuses existing civic and learning stores. Its optional personal profile keeps only user-provided or explicitly confirmed facts, dates, N-400 answers/flags/histories, journey events, confirmed notice fields and checklist completion. It excludes A-number prompts, arbitrary fields, unconfirmed notices, original documents and recordings. Browser profiles are scoped by account ID; guest data is not automatically imported into an account. Browser storage is readable by the browser and is not an encrypted vault. The Profile screen explains this and provides a separate clear action.

Application dates, office and receipt fields are coherent between the Profile and Journey views. Legacy snapshots reuse an already confirmed case fact when the immigration field is missing; explicit edits or clears propagate to both domains without changing the case stage. Structured edits to name, birth date, address, permanent-resident date, N-400 flags or histories invalidate only corresponding older saved practice answers, preventing an old free-form answer from replacing newer confirmed details. Unchanged structured facts preserve confirmed answers. If browser storage rejects a write, the current profile remains usable in memory and the UI explicitly labels those changes as lasting only for the current session. The explicit clear-device-data action also wipes every cached account profile, including inactive accounts, and invalidates pending restore operations so switching accounts cannot resurrect private snapshots.

Cloud profiles are manual snapshots, with a consent checkbox before saving. Local editing does not automatically transmit personal information. Before a save, the client checks whether secure storage is available. Civic data, learning state, official questions and derived study plans are not copied into this snapshot.

## Server configuration

Apply `supabase/migrations/202610050001_brain_profiles.sql` through the normal reviewed migration workflow. It extends existing `user_profiles` and adds separate encrypted `immigration_profiles`, `n400_profiles` and `case_profiles`. The atomic save/delete functions are executable only by `service_role`; RLS denies direct browser access. Every account route verifies the JWT and derives the owner from that token. Deleting an account cascades to these domains.

Set the existing `SUPABASE_URL`, server-only `SUPABASE_SECRET_KEY`, public account configuration and a server-only `PROFILE_ENCRYPTION_KEY` in secure environment settings. `PROFILE_ENCRYPTION_KEY` must contain 32 cryptographically random bytes encoded as base64 (44 characters including the trailing `=`). Never place it in a `VITE_` variable, repository file, log or database record. Preserve this key with the encrypted data; replacing it without decrypting and re-encrypting existing records makes the previous snapshot unreadable. Key rotation requires a separately reviewed migration, not a simple environment replacement.

The API uses AES-256-GCM, a fresh random 12-byte nonce for every domain save, and authenticated context containing the account ID, domain and envelope version. A record cannot be moved to another owner/domain or modified undetected. If the key is absent or invalid, reading and saving fail closed; cloud deletion still works. No server/database credentials or encryption key were fabricated during implementation.

Authenticated endpoints: `GET /account/brain-profile/status`, `GET /account/brain-profile`, `PUT /account/brain-profile` with `{consent:true,profile}`, and `DELETE /account/brain-profile` with `{confirmation:"DELETE_PROFILE"}`. Responses use `Cache-Control: no-store`. Errors contain no profile contents or database detail. Account exports include decrypted saved profile data when the key and migration are available, with a separate availability flag if not. Cloud deletion and local deletion are separate, explicitly confirmed controls.

Migration deployment and live account storage must be verified against the configured Supabase project. Local fixture tests cover encryption integrity, owner/domain isolation, configuration failure, allowlisted persistence, confirmed notices and atomic save/delete contracts. The migration was also executed twice in an isolated PGlite PostgreSQL instance with fixture `auth.users` and `anon`, `authenticated`, `service_role` roles. Validation passed SQL syntax, repeat application, atomic domain save, plaintext-envelope rejection without partial writes, anonymous/authenticated table/function denial, service-role save/delete, profile-only deletion and account-deletion cascades. This validates the SQL locally; it does not claim a remote deployment.
